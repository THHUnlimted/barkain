Sheet S-01

The reframe

Retail arbitrage scans one item at a time in a store aisle. Wholesale sourcing is the opposite motion: a supplier emails a price list, and the job is to find the five winners hiding in three thousand rows. The input surface is a file upload, not a camera — and that one change cascades through every decision in the build.

DimensionBarkain todayM15 Sourcing
InputOne barcode3,000-row CSV / XLSX
QuestionWhere do I buy this cheapest?Which of these should I resell?
OptimizesConsumer out-of-pocketSeller net profit per unit
BudgetLatency — sub-3s, one productThroughput — 3,000 rows, minutes
Output"Buy here, with this card""These 12 rows, ranked, and why"
CachingHostile — prices moveHungry — 12h TTL, re-crunch is free
Unit of workProductList

The consequence that matters: because the unit of work is a list, the expensive resource is external API calls, not milliseconds. Every design choice downstream — the Redis match cache, the skip-before-spend gates, storing the raw match separately from the score — exists to keep a 3,000-row list from becoming 6,000 API calls every time you adjust a threshold.

Sheet S-04

UPC normalization

A barcode scanner hands you a clean 12-digit UPC-A. A distributor spreadsheet hands you whatever survived Excel, a PDF, and three ERP exports. Every one of these failure modes produces a silent lookup miss rather than an error, which is the worst possible bug in a pipeline whose whole job is "did we find this item".

InputCauseHandlingResult
195949036323Clean UPC-AValidate check digitok
1.9594903632E+11Excel float coercionExpand, recompute lost check digitrecovered
1.95949E+11Excel, 6 digits goneDetect precision loss, refusedropped
1234567890111 digits — ambiguousTry both readings, prefer valid checksumflagged
04963406UPC-E compressedGS1 expansion table, verify checkexpanded
0195949036323EAN-13, US prefixStrip to UPC-Aok
10195949036320GTIN-14 case codeUnwrap to the each, search thatunwrapped
"8 12345 67890 1"Human-readable spacingStrip non-digitsok
195949036324Typo — bad check digitKeep digits, never "fix"flagged

Three decisions worth defending

The 11-digit ambiguity is real and unresolvable from length alone. Eleven digits is either a UPC-A whose leading zero Excel ate, or a UPC-A body that never included its check digit. Both are common. We compute the check digit for each reading and prefer the one that validates; when both validate we keep the zero-padded reading and attach AMBIGUOUS_11_DIGIT so the interface can say so rather than pretending.

We refuse to silently repair a bad check digit — with exactly one exception. Guessing which digit was mistyped turns one bad row into one confidently bad row. But scientific notation is different: float rounding eats the least significant digit, which is precisely the check digit. There we know which digit is untrustworthy, so recomputing is a repair, not a guess. When the mantissa lost more than that one digit, the row is failed outright rather than emitted as a well-formed wrong answer that burns an API call and may false-match.

Case codes get unwrapped to the each. Distributor lists are full of GTIN-14 case barcodes, because the distributor sells you a case and prints the case label. But the listing you're pricing against on Walmart is the single unit. Without this derivation those rows come back as clean misses with no explanation — case_gtin_to_each() strips the indicator digit and recomputes the check.

Canonical storage is GTIN-14, because it's the only form that round-trips every input without loss. upc12, ean13 and search_value are derived views that return None when the value genuinely doesn't fit — a case code has no UPC-A form, and returning a truncated 12 digits there would silently turn a case into an each.

Sheet S-05

Spreadsheet ingest

There is no standard for distributor price lists. Across a dozen suppliers the UPC column is called UPC, GTIN, Barcode, EAN, U.P.C. or Item UPC; the cost column is Cost, Your Price, Dealer, Wholesale, WSP or Net; and the whole thing sits under four rows of company letterhead.

Header detection

Scores the first 15 rows. A header row has several populated, mostly-non-numeric cells that match the synonym table. Letterhead has one populated cell; data rows are numeric-heavy.

Column mapping

Keyword scoring, most-specific target resolved first, each column claimed at most once. Exact match beats prefix beats substring, weighted by synonym length.

Value parsing

$1,234.56, (2.50) accounting negatives, 12.5 USD, 1,200, 12 ea, and the em-dash-for-null convention.

The load-bearing detail: resolution order. case_cost resolves before unit_cost. Without that ordering, a list carrying both columns has its case price silently mapped as the unit price — a 12× or 24× cost error that reads as completely plausible and turns every row into an obvious loser. This is the single most common way a hand-built sourcing spreadsheet goes wrong, and it fails quietly in both directions.

When a list gives a case cost and a case pack, unit cost is case_cost ÷ case_pack. When it gives both an explicit unit cost and a case cost that disagree by more than 1%, the explicit unit cost wins and the disagreement is recorded on the row rather than resolved silently.

XLSX support is an optional import — openpyxl in read_only + data_only mode so a 3,000-row workbook isn't fully materialized as cell objects, and so formulas arrive as computed values. If the package is absent the error tells you to export as CSV instead of stack-tracing.

Sheet S-06

Fee engine

Money is Decimal end to end. A fee engine that rounds through float disagrees with the marketplace's own settlement statement by cents per unit — and cents per unit is exactly the margin being argued about.

An unrecognized category resolves to default at 15% rather than being guessed into an 8% bucket. Fee optimism is the expensive kind of wrong: it promotes a losing row to a candidate, and you discover it after the pallet arrives.

What's modelled

ChannelComponents
Walmart WFSReferral % (tiered) + fulfillment by billable weight (6 tiers, oversize and bulky surcharges from length + girth) + storage (cu ft × rate × months, Q4 doubling)
Walmart seller-fulfilledReferral % + your own shipping cost
eBayFinal value fee 13.6% of item + shipping charged, dropping to 2.35% above $7,500 + $0.40 per order + optional ad rate + label cost by weight

Billable weight is the greater of actual and dimensional weight (L×W×H ÷ 139), because that's what carriers bill on and it routinely shifts a light bulky item up a whole fee tier. eBay revenue includes buyer-paid shipping on both sides of the ledger — otherwise a $10 item with $6 shipping looks like a loser next to a $16 item with free shipping, when they are the same trade.

Treat every rate table as configuration, not truth. Marketplace fee schedules change on the marketplace's schedule. Each table cites its source and verification date and the module carries FEE_SCHEDULE_VERSION = "2026-07-26". When a verdict looks wrong the first question is always "is the rate card current" — a stale referral rate is a silent two-point margin error across every row of every list. These are published US rates; negotiated rates, fee holidays and account-specific exceptions are not modelled. Re-derive them from your own settlement reports before running real money through this.

Not modelled: returns, chargebacks, WFS inbound freight, prep and labeling, shrink, and the cost of your own time. A 25% ROI floor is doing the work of absorbing those — which is why the default threshold is 25% and not 5%.

When weight or dimensions are unknown, the engine substitutes a documented default and tags the result assumed_weight / assumed_cubic_feet. That flag rides all the way to the verdict, so a candidate built on a guessed weight is visibly different from one built on measured dimensions and can never reach pass silently.

Sheet S-06b

Landed cost

The number on the price list is the invoice cost. By the time a unit is sellable it has also absorbed freight, prep, packaging, duty, payment fees, and a share of the units that arrived broken or came back. Scoring on invoice cost overstates margin — and it overstates it unevenly, which is what makes it dangerous. It doesn't shift every row by the same amount; it reorders them.

GrainComponentsAllocation
Per shipmentLTL freight, customs entry, palletSplit across units per_unit / by_weight / by_cube — freight is billed by weight, so a heavy SKU and a light one in the same truck must not split it evenly
Per caseInbound handling, case labelsDivided by case pack
Per unitPolybag, label, prep labor, inspection, the unit's own boxDirect
Rate on goodsDuty / tariff, payment or FX feeMultiplied against invoice value — real cash out
ReserveShrink, unsellable returnsDivides, doesn't add — see below

Reserves divide, they don't add. You don't pay shrink and returns per unit — you lose that fraction of units, and the survivors have to carry the cost of all of them. A 3% shrink and 5% return rate means 92 units carry the cost of 100, which is an 8.7% cost increase, not 8%. Adding the rates instead of dividing by the survival rate understates the hit at exactly the rates that matter.

Every component is optional and defaults to zero, with an assumptions flag recording what was left unspecified — an invented freight number that happens to be wrong is worse than a visible gap, because it looks like it was measured. A LandedCost carrying nothing but invoice_cost behaves exactly like the raw-cost path.

landed cost — freight $0.42/lb + $0.83 prep/pack/QC + 3% return reserve

     freight $0.88 | prep $0.55 | pack $0.18 | QC $0.10 | survives 97%
  Bluetooth Earbuds Pro              invoice $  40.00 -> landed $  42.35 (+5.9%)
     freight $0.25 | prep $0.55 | pack $0.18 | QC $0.10 | survives 97%
  Dog Chew Toy Variety 5-pack        invoice $   4.00 -> landed $   4.98 (+24.5%)
     freight $0.00 | prep $0.55 | pack $0.18 | QC $0.10 | survives 97%
  Air Purifier HEPA Medium Room      invoice $ 180.00 -> landed $ 192.48 (+6.9%)
     freight $5.88 | prep $0.55 | pack $0.18 | QC $0.10 | survives 97%

The uplift ranges from 5.9% to 24.5% across four rows of the same list — a 4× spread. That's the entire argument: a flat "add 15% for costs" rule would make the earbuds look worse than they are and the dog toys look better. Returns are reserved at 3% here, a deliberate cushion above the measured sub-1% rate; the reserve absorbs the damage and shrink that aren't separately measured, and being wrong in that direction costs a marginal row while being wrong the other way costs a pallet.

Sheet S-06c

Selling plans and subscriptions

A monthly subscription is a fixed cost, and the instinct — take Amazon's $39.99, divide by expected units, add it to every row — is a real and expensive mistake in both directions.

  • If you already pay it, it's sunk for the next SKU decision. Loading a share onto every candidate makes marginal-but-real winners look like losers, and you decline orders that would have made money.
  • If you don't yet pay it, it isn't per-unit at all — it's a threshold question, and "does this plan pay for itself" has a volume answer, not a per-unit one.

So the module does two separate things and never mixes them. Marginal rates — an eBay Store's FVF cut, Amazon Individual's $0.99/item — are genuinely per-unit and flow into the fee engine. Fixed fees are reported once per channel as a breakeven volume.

Sheet S-06d

Fee calibration — your settlements beat any rate card

Published rate cards are an approximation of what you actually get charged. They don't know your contract-category assignments, your incentive programs, or that a rate changed last Tuesday. Your settlement report knows all of it, because it is what happened.

The first real reconciliation import proved the point in one row.

FeePublishedActualVerdict
Referral, Automotive & Powersports12.00%12.00%confirmed — the reason to trust the table for products you haven't sold
WFS fulfillment, 16 oz item$3.45 / $4.95$4.45neither tier — sits between the published 0–1 lb and 1–2 lb bands
Net proceeds on the order$4.38$3.4629% optimistic

So the rule is: an observed fee always beats a published rate. Published tables become the fallback for products you've never sold, and every import shrinks that set.

Why $4.45 matched no weight tier

A settlement report answered it outright. Every one of twelve FulfillmentFee rows for an $8.99 item carried:

settlement.csv — the column that explained the mismatch
  Transaction Type   FulfillmentFee
  Billing Method     Under$10
  Net Payable        4.45      x12 lines, across three separate weeks

WFS prices items under $10 on a separate flat schedule, not on the weight tiers at all. That's why $4.45 sat between the published 0–1 lb ($3.45) and 1–2 lb ($4.95) bands — it was never being priced by weight. It's the kind of rule that's easy to miss on a rate card and impossible to miss in a settlement, and it matters disproportionately for wholesale: sub-$10 items are exactly where thin margins live, so mispricing their fulfillment by a dollar decides the whole category.

With the rule encoded, the engine reproduces the real order exactly: commission $1.08, WFS $4.45, net $3.46.

Two traps in the same file. One order billed $2.95 rather than $4.45 — a $1.50 discount — followed by a separate DiscountAdjustment line recouping it, because "a discount was applied in error." Calibrating on net payable would have taught a fulfillment fee that isn't real; the parser uses the pre-discount amount and reports clawbacks separately.

And Walmart's own reports disagree on category names: the reconciliation report calls this item Automotive & Powersports, the settlement calls it Vehicles, Parts & Accessories. Same item, same 12%. Both spellings have to resolve to one key or the calibration splits in two and each half looks under-sampled.

same order, both ways — actual was commission $1.08, WFS $4.45, net $3.46

    ['assumed_cubic_feet']

FeeCalibration aggregates observations by category, SKU and product type, using medians rather than means so one promotional order can't move the estimate. Sample counts ride along, so a verdict can distinguish "measured 40 times" from "measured once".

Two details the parser has to get right

  • WFS fulfillment posts as a separate adjustment row, sometimes under a different purchase order and in a different settlement period than the sale it belongs to. Matching is by Purchase Order #, not row adjacency.
  • Long-term storage has no purchase order at all — it posts against inventory. Those lines are emitted as synthetic rows rather than dropped, because storage is precisely the fee that punishes slow movers, and a parser that silently discards it would make dead stock look free.

The two channels compute their fee base in opposite directions, and both were verified from real documents:

eBay charges its percentage on the sales tax it collects. $26.50 item + $0.00 shipping + $1.86 tax = $28.36 base × 13.6% = $3.86. Computing on item price alone understated the fee by ~7%. The per-order fixed fee is also tiered on order total — $0.40 above $10.01, $0.30 at or below — and Promoted Listings ad fees use the same tax-inclusive base ($2.55 / $28.36 = exactly 9.0%, the set ad rate).

Walmart does not. $1.08 commission on an $8.99 item is 12.00% of the price flat; the $0.69 tax was collected and withheld as a pass-through that never entered the base.

The corrected model now reproduces the sample eBay order to the cent: FVF $4.26, label $5.83, ad $2.55, earnings $13.86.

Sheet S-07

Popularity — the 99% of the battle

Margins are arithmetic. Whether the thing sells is the actual question, and every marketplace is deliberately unhelpful about it. So the engine ranks its signals by how close each one is to counting units, and carries that ranking all the way to the screen. A verdict built on observed stock movement and one built on a lifetime review total must not look the same.

TierSignalSourceHow close to truth

Inventory depletion — the definitive method

This is the answer to "is there something better than review velocity", and it is a large step up. Poll a listing's purchasable quantity, walk the observations in time order, and sum the decreases. An increase is a restock — reset the baseline and count nothing. That sum is units sold: not modelled, observed.

Two properties make it the best signal available:

  • It measures a specific seller, not the listing. Every other signal describes the whole listing and then has to be divided by a guessed seller count. Depletion already is the per-offer number, so the engine skips the unit-share division entirely for it — dividing again would understate a good row by a factor of five.
  • It works on all three channels, with no API approval, no subscription, and no dependence on buyer behavior.

The guard that makes it usable. A listing reporting 400 units on Monday and 0 on Tuesday almost certainly went out of stock or had a feed error — it did not sell 400 units in a day. Any single-interval drop exceeding 75% of the running baseline is discarded as a correction. Without that guard, one bad observation produces a phantom top-ranked row, which on a velocity-first ranking is the worst failure the system can have.

The cost: one probe per SKU per day, and cart-level probing is heavier than a page read. This should run against the shortlist — rows that already cleared the fee gates — not against all 3,000 rows of every list. Roughly 50–200 SKUs polled daily, not 3,000.

What changed on eBay

The original plan routed exact sold-counts through eBay's Marketplace Insights API. As of mid-2026 that is a Limited Release effectively closed to anyone who isn't a major partner — developers report being denied outright. Terapeak / Product Research inside Seller Hub is the real path: free with a seller account, gives exact units sold over a window, and is an authenticated page rather than an API. So it's an import/session-scrape, not an API call. sold_count_window_days is carried explicitly on the snapshot so a 30-day Product Research export isn't silently divided by three like a 90-day one.

Where a channel gives nothing better, unit share still converts listing-wide demand into your demand: estimated_monthly_sales ÷ (seller_count + 1). The +1 is you. Five sellers on a 300-unit/month item is 50 each and a real business; five on a 40-unit/month item is a price war with extra steps.

The moat is a table that has to start filling before it's worth anything. Depletion and review velocity both require longitudinal data that cannot be bought or backfilled — you cannot go back and observe last Tuesday's stock count. listing_snapshots is written on every live match, not only by the cron, so it accumulates from the first crunch. Cached matches are deliberately skipped: re-storing identical numbers under a new timestamp would fabricate a flat history and make a volatile item look stable.

Price stability comes from the same table: coefficient of variation (σ/μ), scale-free so 5% movement means the same thing on a $12 item and a $400 one. Fewer than three observations returns stable rather than volatile — "we haven't watched long enough" must not read as a red flag.

Sheet S-08

Verdict scoring

Deterministic, zero LLM — per Barkain's own classification rule a profit calculator is Traditional, and an answer someone is about to spend $4,000 on should be reproducible and auditable rather than resampled.

pass

Every hard threshold cleared and no soft flags. Act on it.

watch

No hard failure, but something we can't yet tell — no demand history, no distributor, an assumed weight. Re-crunch after the snapshot worker runs.

fail

A hard threshold failed. It loses money, nobody buys it, or the competition is already too deep.

Three outcomes rather than two, because a binary pass/fail throws away the most interesting rows. Something that clears every profit threshold but has unknown demand isn't a failure — it's a row where the snapshot database hasn't run long enough yet, and it should come back next week. watch is also the queue that tells the snapshot worker which listings are worth polling.

Ranking: velocity beats margin

Rows sort by annualized ROI — not margin, not raw monthly profit. For a capital-constrained buyer the scarce resource is cash, and what matters is how many times a year that cash comes back with a profit attached.

annualized_roi = roi_pct × 365 ÷ (days_to_sell_through + reorder_lead_time)

A 60% margin turning over twice a year is a worse use of a purchase order than 22% turning over eleven times. The second earns more on the same dollar, with less shelf risk, less price-war exposure, and less chance of holding dead stock into Q4 storage rates.

Lead time in the denominator is not a detail. Capital doesn't redeploy when the last unit ships — it redeploys when the next case lands. An item that clears in six days on a three-week reorder cycle turns over about 14 times a year, not 60. Building the metric without lead time produced four-figure percentages on every fast mover in testing and reordered the whole list on an artifact of the formula.

The slider

velocity_bias is a continuous 0.0–1.0 dial, not a mode switch. Drag it and the list reorders between the two things a buyer might mean by "best".

BiasRanks byWho wants this
0.00Net dollars per unitStorage is free, cash isn't tight, you'd rather touch fewer units
0.50Geometric mean of bothA row has to be genuinely decent on both axes
0.75Weighted toward turns (default)Capital-constrained, reordering regularly
1.00Annualized ROIPure velocity — churn the cash as fast as it will go

The blend is a weighted geometric mean, not arithmetic. Arithmetic lets one axis rescue a zero on the other — a 900%-annualized row making $0.02 a unit would still place well at "balanced", which is not what balanced means to anyone. Geometric requires a row to be decent on both axes to score in the middle, which is the intuition the dial is supposed to express.

Both axes are normalized against the visible list before blending, so the dial behaves identically on a list of $4 consumables and a list of $400 tools. The margin axis is dollars per unit, not margin percent — a 90% margin on a $2 item isn't what someone dragging toward "margin" is asking for.

  bias 0.00  (margin)       0.100              0.900          fat
  bias 0.25                 0.173              0.520          fat
  bias 0.50  (balanced)     0.300              0.300          tie
  bias 0.75  (default)      0.520              0.173          fast
  bias 1.00  (velocity)     0.900              0.100          fast

Verdict tier remains the primary sort key at every position on the dial, so no amount of blended score floats a fail above a pass. Reorder lead time is per-product — the supplier who ships a case in four days is not the one who takes nine weeks on a container, and a single global number flattens exactly the difference that decides between two otherwise equal rows.

Each channel also reports a breakeven sale price: the lowest price that still clears zero, holding fixed fees constant. When five sellers are racing each other down, that's a far more actionable number than the current buy box.

And on the part software can't automate — whether an authorized distributor will actually sell to you, and whether the brand is gated on your seller account — brand_access keeps a per-brand ledger and candidates on unknown brands auto-generate a distributor inquiry draft. Restricted brands are demoted, not hidden: knowing there's a $9/unit spread behind a gate is exactly what tells you which gating application to file.

Sheet S-08b

Projected vs. actual — the loop that makes it converge

Every demand number the scanner produces is an estimate with a known error profile. BSR curves run 20–40% off. Review velocity rests on a 2% constant that varies by category. Depletion is good but samples one offer. Right now those errors are unmeasured, which means they're unmanaged.

The fix is boring and powerful: write down every prediction at the moment it's made, then compare it against what actually sold. Both marketplaces expose first-party seller APIs for this — no scraping, no approval gauntlet, because it's your own data.

ChannelAPIGives
WalmartOrders APIShipped units per SKU per window
Reports API — reconciliationRealized revenue and every fee. Already parsed by recon.py
Insights APIListing-level performance and listing quality
eBaySell Fulfillment getOrdersActual units sold
Sell Finances getTransactionsExact realized fees, per order
Sell Analytics getTrafficReportImpressions, listing views, sales conversion rate

The eBay traffic report is a genuine bonus. Conversion rate is the missing term in every demand estimate — knowing a listing got 4,000 impressions and converted at 1.2% explains a miss in a way a units number never can. It separates "nobody wants this" from "nobody saw this", and those call for opposite responses.

Worth noting the contrast with Sheet S-07: eBay's Marketplace Insights API (competitor sold data) is effectively closed, but the Sell APIs covering your own account are open to any seller with a dev key. The hard data to get is other people's; your own is available.

Using the billed count as a demand estimate under-reads demand by the entire in-flight backlog — here 3 of 14 units, or 21%. That's not noise, it's a systematic downward bias, and it biases every reorder decision in the same direction. Orders for demand, billed for cash. The scanner now models them as separate estimators for exactly this reason.

The inventory reconciliation report is also the depletion signal without the inference. For SKUs you already own, Walmart reports units shipped directly, with Lost / Found / Removed / Transferred broken into their own columns — so the restock detection and outlier guarding that the cart-quantity estimator has to do is simply handled at the source. Cart scraping is what that approximates for prospective items you don't own yet.

What the loop learns

Pairing matches each actual to the latest forecast made before the window opened — a prediction made after the sales it's judged on isn't a prediction. Two things fall out:

simulated: BSR runs hot in Pet Supplies, depletion is accurate
  SCOREBOARD
    comparisons          12
    median_ratio         0.805      actual / predicted
    mape                 20.2%
    within_25_pct        50.0%
    over_predicted_pct   66.7%      the direction that buys dead stock

  LEARNED CORRECTIONS
    tier observed              n=6   ratio 1.01   mape  3.0%   -> apply 1.01
    tier rank                  n=6   ratio 0.625  mape 37.5%   -> apply 0.625
    net per unit bias          n=12  ratio 0.942          -> points at fees, not demand

  APPLIED TO A FRESH ESTIMATE
    rank / Pet Supplies   200 units -> 125  (tier+category_n6)
    observed / Automotive 200 units -> 202  (tier+category_n6)
    rank / Toys (unseen)  200 units -> 125  (tier_n6, falls back to the tier)
  • Per-tier bias. If rank consistently predicts 1.6× what you sell in Pet Supplies, that's a correction factor, not noise. The more specific (tier, category) key wins when it has samples; otherwise it falls back to the tier.
  • Honest confidence. A tier within 15% across 40 SKUs deserves to promote a row to pass. A tier that's been off by 3× deserves watch no matter how good the margin looks.

Three guards keep the loop from learning the wrong lesson. Corrections are reported below five paired samples but not applied — two data points can produce a 0.4× factor that's pure chance, and a premature correction moves every row while looking authoritative. Factors are clamped to 0.25×–4×, because anything outside that almost always means a mis-paired SKU rather than genuinely 6×-off demand. And medians, not means, so one viral week can't permanently reset the model.

The net_per_unit bias is tracked separately on purpose. Running below 1.0 means the fee and landed-cost model is optimistic — a recon.py problem, not a demand problem. Saying which one is wrong saves an afternoon of tuning the wrong thing.

Forecasts are recorded only for rows you actually purchase. A prediction for something never bought has no actual to compare against, so storing it would add noise to the accuracy numbers without adding information. Each row carries the fee_schedule_version and thresholds that produced it, so a forecast made under an old rate card isn't silently judged against actuals from a new one.

Like the snapshot table, this can't be bought or borrowed — it depends on your categories, your price points, your listings. It starts compounding the first time you buy something the tool recommended.

Sheet S-10

Data model

TableGrainNotes
sourcing_listsOne uploaded price listColumn mapping + normalization stats + thresholds + verdict summary, all JSONB
sourcing_rowsOne distributor linematch (what the APIs said) and channels (what we concluded) stored separately
listing_snapshotsOne observationTimescaleDB hypertable on captured_at, PK (channel, listing_key, captured_at)
sourcing_forecastsOne predictionWritten only for rows you actually buy. Carries the fee-schedule version that produced it
sourcing_actualsOne SKU, one windowUnits + net proceeds from the seller APIs. Unique on the window so re-imports update rather than fake confidence
brand_accessOne brand, per userauthorized / restricted / pending / unknown + distributor contact

Why match and score are separate columns. Re-scoring on new thresholds reads match and rewrites channels — no refetch, no rate-limit exposure, instant. "What if I dropped my ROI bar to 20%" should cost zero API calls, and a fee-schedule correction should be replayable over every historical list.

Why sourcing rows never write to products. A distributor list is 3,000 speculative UPCs, most of which will never be bought and many of which won't resolve. Writing them into Barkain's consumer products table would pollute Recently Sniffed, dilute the pg_trgm search index, and blow out the resolve cache with rows nobody asked for.

Why snapshots are keyed on the channel's listing, not the sourcing row. Snapshots outlive the list that created them — that's the entire point. History survives list deletion and is shared across every user who ever sources the same item. On eBay the key is GTIN-scoped rather than item-scoped, because individual listings end and relist under new IDs; the market for a GTIN is the thing with continuity.

Migration 0013 is written and staged at sourcing/migrations/ but deliberately not dropped into infrastructure/migrations/versions/ — moving it there is what arms it. Constraints are mirrored in __table_args__ so Base.metadata.create_all matches Alembic, following the parity pattern from migrations 0003 / 0006 / 0009–0012.
