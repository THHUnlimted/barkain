Sheet S-01

The reframe

Retail arbitrage scans one item at a time in a store aisle. Wholesale sourcing is the opposite motion: a supplier emails a price list, and the job is to find the five winners hiding in three thousand rows. The input surface is a file upload, not a camera — and that one change cascades through every decision in the build.

DimensionBarkain todayM15 Sourcing
InputOne barcode3,000-row CSV / XLSX
QuestionWhere do I buy this cheapest?Which of these should I resell?
OptimizesConsumer out-of-pocketSeller net profit per unit
BudgetLatency — sub-3s, one productThroughput — 3,000 rows, minutes
Output"Buy here, with this card""These 12 rows, ranked, and why"
CachingHostile — prices moveHungry — 12h TTL, re-crunch is free
Unit of workProductList

The consequence that matters: because the unit of work is a list, the expensive resource is external API calls, not milliseconds. Every design choice downstream — the Redis match cache, the skip-before-spend gates, storing the raw match separately from the score — exists to keep a 3,000-row list from becoming 6,000 API calls every time you adjust a threshold.

Why the pure/impure split is drawn where it is. Six of the thirteen modules have no imports beyond the standard library and each other. Sheet S-04

UPC normalization

A barcode scanner hands you a clean 12-digit UPC-A. A distributor spreadsheet hands you whatever survived Excel, a PDF, and three ERP exports. Every one of these failure modes produces a silent lookup miss rather than an error, which is the worst possible bug in a pipeline whose whole job is "did we find this item".

InputCauseHandlingResult
195949036323Clean UPC-AValidate check digitok
1.9594903632E+11Excel float coercionExpand, recompute lost check digitrecovered
1.95949E+11Excel, 6 digits goneDetect precision loss, refusedropped
1234567890111 digits — ambiguousTry both readings, prefer valid checksumflagged
04963406UPC-E compressedGS1 expansion table, verify checkexpanded
0195949036323EAN-13, US prefixStrip to UPC-Aok
10195949036320GTIN-14 case codeUnwrap to the each, search thatunwrapped
"8 12345 67890 1"Human-readable spacingStrip non-digitsok
195949036324Typo — bad check digitKeep digits, never "fix"flagged

Three decisions worth defending

The 11-digit ambiguity is real and unresolvable from length alone. Eleven digits is either a UPC-A whose leading zero Excel ate, or a UPC-A body that never included its check digit. Both are common. We compute the check digit for each reading and prefer the one that validates; when both validate we keep the zero-padded reading and attach AMBIGUOUS_11_DIGIT so the interface can say so rather than pretending.

We refuse to silently repair a bad check digit — with exactly one exception. Guessing which digit was mistyped turns one bad row into one confidently bad row. But scientific notation is different: float rounding eats the least significant digit, which is precisely the check digit. There we know which digit is untrustworthy, so recomputing is a repair, not a guess. When the mantissa lost more than that one digit, the row is failed outright rather than emitted as a well-formed wrong answer that burns an API call and may false-match.

Case codes get unwrapped to the each. Distributor lists are full of GTIN-14 case barcodes, because the distributor sells you a case and prints the case label. But the listing you're pricing against on Walmart is the single unit. Without this derivation those rows come back as clean misses with no explanation — case_gtin_to_each() strips the indicator digit and recomputes the check.

Canonical storage is GTIN-14, because it's the only form that round-trips every input without loss. upc12, ean13 and search_value are derived views that return None when the value genuinely doesn't fit — a case code has no UPC-A form, and returning a truncated 12 digits there would silently turn a case into an each.

Sheet S-05

Spreadsheet ingest

There is no standard for distributor price lists. Across a dozen suppliers the UPC column is called UPC, GTIN, Barcode, EAN, U.P.C. or Item UPC; the cost column is Cost, Your Price, Dealer, Wholesale, WSP or Net; and the whole thing sits under four rows of company letterhead.

Header detection

Scores the first 15 rows. A header row has several populated, mostly-non-numeric cells that match the synonym table. Letterhead has one populated cell; data rows are numeric-heavy.

Column mapping

Keyword scoring, most-specific target resolved first, each column claimed at most once. Exact match beats prefix beats substring, weighted by synonym length.

Value parsing

$1,234.56, (2.50) accounting negatives, 12.5 USD, 1,200, 12 ea, and the em-dash-for-null convention.

The load-bearing detail: resolution order. case_cost resolves before unit_cost. Without that ordering, a list carrying both columns has its case price silently mapped as the unit price — a 12× or 24× cost error that reads as completely plausible and turns every row into an obvious loser. This is the single most common way a hand-built sourcing spreadsheet goes wrong, and it fails quietly in both directions.

When a list gives a case cost and a case pack, unit cost is case_cost ÷ case_pack. When it gives both an explicit unit cost and a case cost that disagree by more than 1%, the explicit unit cost wins and the disagreement is recorded on the row rather than resolved silently.

XLSX support is an optional import — openpyxl in read_only + data_only mode so a 3,000-row workbook isn't fully materialized as cell objects, and so formulas arrive as computed values. If the package is absent the error tells you to export as CSV instead of stack-tracing.

Sheet S-06

Fee engine

Money is Decimal end to end. A fee engine that rounds through float disagrees with the marketplace's own settlement statement by cents per unit — and cents per unit is exactly the margin being argued about.

An unrecognized category resolves to default at 15% rather than being guessed into an 8% bucket. Fee optimism is the expensive kind of wrong: it promotes a losing row to a candidate, and you discover it after the pallet arrives.

What's modelled

ChannelComponents
Walmart WFSReferral % (tiered) + fulfillment by billable weight (6 tiers, oversize and bulky surcharges from length + girth) + storage (cu ft × rate × months, Q4 doubling)
Walmart seller-fulfilledReferral % + your own shipping cost
eBayFinal value fee 13.6% of item + shipping charged, dropping to 2.35% above $7,500 + $0.40 per order + optional ad rate + label cost by weight

Billable weight is the greater of actual and dimensional weight (L×W×H ÷ 139), because that's what carriers bill on and it routinely shifts a light bulky item up a whole fee tier. eBay revenue includes buyer-paid shipping on both sides of the ledger — otherwise a $10 item with $6 shipping looks like a loser next to a $16 item with free shipping, when they are the same trade.

Treat every rate table as configuration, not truth. Marketplace fee schedules change on the marketplace's schedule. Each table cites its source and verification date and the module carries FEE_SCHEDULE_VERSION = "2026-07-26". When a verdict looks wrong the first question is always "is the rate card current" — a stale referral rate is a silent two-point margin error across every row of every list. These are published US rates; negotiated rates, fee holidays and account-specific exceptions are not modelled. Re-derive them from your own settlement reports before running real money through this.

Not modelled: returns, chargebacks, WFS inbound freight, prep and labeling, shrink, and the cost of your own time. A 25% ROI floor is doing the work of absorbing those — which is why the default threshold is 25% and not 5%.

When weight or dimensions are unknown, the engine substitutes a documented default and tags the result assumed_weight / assumed_cubic_feet. That flag rides all the way to the verdict, so a candidate built on a guessed weight is visibly different from one built on measured dimensions and can never reach pass silently.

Sheet S-07

Demand estimation, and the thing nobody can copy

Walmart doesn't publish sales figures and neither does eBay for active listings. So every number here is a proxy, and the honest move is to rank the proxies by trustworthiness and carry that ranking all the way to the interface. A verdict built on a direct sold-count and one built on a single lifetime review total should not look the same on screen.

TierSignalMethodActionable?
directeBay sold count, 90dMarketplace Insights ÷ 3. Not an estimate — the number.yes
velocityReview deltaΔreviews ÷ days × 30 ÷ 2% review rate. Needs 2 snapshots ≥7 days apart.yes
badge"500+ bought yesterday"Coarse, and a floor rather than a point estimate. Same-day truth.yes
heuristicLifetime reviews ÷ age4,000 reviews over six years says almost nothing about this month.ranks only
unknownNothingNo listing, or a listing with no signal.no

Unit share converts market demand into your demand: estimated_monthly_sales ÷ (seller_count + 1). The +1 is you joining the listing. Five sellers on a 300-unit/month item is 50 units each and a real business; five sellers on a 40-unit/month item is a price war with extra steps.

The moat is a table that has to start filling before it's worth anything. Review velocity requires longitudinal data that cannot be bought or backfilled — you cannot go back and observe last month's review count. listing_snapshots is written on every live match, not only by the cron, so the dataset starts accumulating from a user's very first crunch. Cached matches are deliberately skipped: re-storing identical numbers under a new timestamp would fabricate a flat price history and make a volatile item look stable.

This is also the honest limitation. For roughly the first two weeks, the tool is a very good fee calculator with a demand column that says "not yet". That's not a flaw in the plan — it is the plan, and it's the part a competitor launching later cannot shortcut.

Price stability comes from the same table: coefficient of variation (σ/μ) over the observed window, which is scale-free so 5% movement means the same thing on a $12 item and a $400 one. Fewer than three observations returns stable rather than volatile — "we haven't watched long enough" must not read as a red flag, or every new list would fail the stability gate on its first crunch.

Sheet S-08

Verdict scoring

Deterministic, zero LLM — per Barkain's own classification rule a profit calculator is Traditional, and an answer someone is about to spend $4,000 on should be reproducible and auditable rather than resampled.

pass

Every hard threshold cleared and no soft flags. Act on it.

watch

No hard failure, but something we can't yet tell — no demand history, no distributor, an assumed weight. Re-crunch after the snapshot worker runs.

fail

A hard threshold failed. It loses money, nobody buys it, or the competition is already too deep.

Three outcomes rather than two, because a binary pass/fail throws away the most interesting rows. Something that clears every profit threshold but has unknown demand isn't a failure — it's a row where the snapshot database hasn't run long enough yet, and it should come back next week. watch is also the queue that tells the snapshot worker which listings are worth polling.

Default thresholds

GateDefaultKindRationale
Net profit / unit$3.00hardBelow this, returns and shrink eat it
ROI25%hardAbsorbs the unmodelled costs
Monthly unit share30hardBelow this it isn't worth the SKU slot
Price stabilityCV ≤ 0.15hardA 30% swing is a price war you'd be joining
Capital per SKUoptionalhardA great ratio needing a $9k pallet isn't a candidate on a $5k budget
Max sellersoptionalhardOff by default — unit share already prices competition
Brand access—softRestricted brands are demoted, never hidden

Ranking is by projected monthly profit — net_profit × unit_share — not by margin or ROI. A 60% margin on something that sells twice a month is a worse use of a purchase order than 22% on something that moves 400 times, and sorting by margin is exactly how sourcing spreadsheets talk people into slow-moving inventory. Verdict tier is the primary sort key, so no amount of projected profit floats a fail above a pass.

Each channel also reports a breakeven sale price: the lowest price that still clears zero, holding fixed fees constant. When five sellers are racing each other down, that's a far more actionable number than the current buy box.

And on the part software can't automate — whether an authorized distributor will actually sell to you, and whether the brand is gated on your seller account — brand_access keeps a per-brand ledger and candidates on unknown brands auto-generate a distributor inquiry draft. Restricted brands are demoted, not hidden: knowing there's a $9/unit spread behind a gate is exactly what tells you which gating application to file.

Sheet S-10

Data model

TableGrainNotes
sourcing_listsOne uploaded price listColumn mapping + normalization stats + thresholds + verdict summary, all JSONB
sourcing_rowsOne distributor linematch (what the APIs said) and channels (what we concluded) stored separately
listing_snapshotsOne observationTimescaleDB hypertable on captured_at, PK (channel, listing_key, captured_at)
brand_accessOne brand, per userauthorized / restricted / pending / unknown + distributor contact

Why match and score are separate columns. Re-scoring on new thresholds reads match and rewrites channels — no refetch, no rate-limit exposure, instant. "What if I dropped my ROI bar to 20%" should cost zero API calls, and a fee-schedule correction should be replayable over every historical list.

Why sourcing rows never write to products. A distributor list is 3,000 speculative UPCs, most of which will never be bought and many of which won't resolve. Writing them into Barkain's consumer products table would pollute Recently Sniffed, dilute the pg_trgm search index, and blow out the resolve cache with rows nobody asked for.

Why snapshots are keyed on the channel's listing, not the sourcing row. Snapshots outlive the list that created them — that's the entire point. History survives list deletion and is shared across every user who ever sources the same item. On eBay the key is GTIN-scoped rather than item-scoped, because individual listings end and relist under new IDs; the market for a GTIN is the thing with continuity.

Migration 0013 is written and staged at sourcing/migrations/ but deliberately not dropped into infrastructure/migrations/versions/ — moving it there is what arms it. Constraints are mirrored in __table_args__ so Base.metadata.create_all matches Alembic, following the parity pattern from migrations 0003 / 0006 / 0009–0012.

What came from Barkain

The reason to build this inside Barkain rather than greenfield: roughly 60% of the hard parts already exist and are proven against live retailers.

ComponentReuse
eBay Browse adapterOAuth token cache, 2h TTL with refresh buffer, condition-ID buckets, normalized listing mapping. M15 adds a gtin= path on the same token.
Walmart HTTP adapterDecodo residential proxy + PerimeterX retry budget. The fallback leg, and the only path that yields review counts and the "bought yesterday" badge.

SSE plumbingsse_event() + the iOS byte-level splitter. A 3,000-row crunch is exactly the shape SSE was built for.

The relevance gates that dominate Barkain's consumer path — brand-bleed, token overlap, model-number matching — mostly stop mattering here, because sourcing matches by exact UPC. They come back only for the fallback title-search path when a UPC has no listing.

Sheet S-13

Open questions

Answers to these change what gets built next, so they're worth settling before the router and tests go in.

QuestionWhy it matters
Do you have Walmart.io credentials, or should the Walmart leg default to the residential-proxy scrape?The scrape is the only path that returns review counts and the "bought yesterday" badge — which are two of the four demand signals. If the API is the only path, demand estimation is thinner than designed.
Is Amazon a third channel?Keepa is already on the Phase 4 roadmap. Adding it later is a new adapter plus a fee table; designing for it now costs nothing.
Single seller, or multi-tenant?brand_access is currently scoped per user. Thresholds are per list. Both assumptions get expensive to change after data exists.
Web dashboard or iOS?A 3,000-row ranked table wants a wide screen and CSV export. The existing iOS app is the wrong shape for this workflow — the phone is for the store aisle, not the price list.
What are your actual thresholds?The $3 / 25% / 30-units defaults are the common ones, but they should be yours.
